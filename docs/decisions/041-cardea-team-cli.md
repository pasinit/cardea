# ADR-041: `cardea team`, the team commands in the installed CLI

- **Date / owner / milestone:** 2026-11-23; team-kit and packaging maintainers; agent teams (ADR-034, ADR-040), Debian package.
- **Status:** implemented; portable tests only. The candidate evaluation is **provisional**: it was written without network access, so versions and licences are not checked. The package was not built and `sudoers` was not exercised on a Debian host here (`visudo -cf` runs in the postinst and `container_build.sh`).
- **Requirement:** a plain user types `cardea team status` (and `pause`, `resume`, `stop`, `apply`, `render`, `provision`, `settings`, `set`, `mail`) and it works, though the supervisor's SVID is bound to the `cardea-kernel` uid.
  - The commands run the team kit shipped in the package, with the package's code (the same version as the running kernel), not a checkout.
  - Authority stays kernel-checked, no credential is exposed, the privilege rule is narrow, the team stays configuration, and the repository holds no personal data or hosts.
- **Candidates (provisional):** `sudo` rule to the account; polkit `pkexec`; a systemd socket-activated service as `cardea-kernel`; a setuid wrapper; `doas`. Primary sources not fetched; versions not checked.
  - `sudo` is already a package dependency and the package already ships a sudoers rule (`cardea-host`). A rule with the fixed command and an empty argument list is exact.
  - polkit and a socket-activated service need a new daemon or a D-Bus policy and a second authorization layer for one command. A setuid wrapper is a new privileged binary. `doas` is not in the package's tested profile.
- **Decision:** sudo, with the narrowest form it allows.
  - `%cardea-operators ALL=(cardea-kernel) NOPASSWD: /usr/libexec/cardea-team-run ""`: one program, no arguments (so no wildcard), one runas account. The group is created empty; the host owner adds people. Root also works.
  - The front end (`cardea team`, running as the user) parses, validates and asks the questions (confirm a settings change or a stop). It sends one JSON request on the helper's stdin. The helper (`cardea.service.team_cli.helper_main`) is the only code that runs as `cardea-kernel`.
  - **The host file is fixed** to `/etc/cardea/team.host.json` through the helper; it must be a regular file owned by root or `cardea-kernel` and writable by no one else. A host file names the SPIFFE ID and socket the supervisor presents, so a caller-chosen one would let a caller aim the account's SVID. `--host` works only when already running as `cardea-kernel`. `render --out` is written by the front end as the user, from text the helper returns, so the helper writes nowhere the caller names.
  - **Same code as the kernel:** `stage.py` copies `deploy/team-kit` (scripts, pages, example host file; no fixtures) to `/usr/lib/cardea/team-kit`, and the helper imports `cardea.service` from `/usr/lib/cardea`. Under that root, `teamkit.provision_command` runs `provision` as the interpreter on the package's `main.py`, whatever the host file's `provisioning.cardea` says.
  - **No model decides anything:** the helper calls the kit, which calls the kernel as the supervisor. A refusal is reported by exception type and kernel error code. Output to the terminal has control characters removed (mail from agents is untrusted data).
  - **Settings:** `set <key> <value>` builds a settings document for the dashboard's model (`teamsettings.py`), so validation is the same code. The email rate limit was not a dashboard setting; it is now (`email_rate_limit`), for both. The token a preview prints is sent back on confirm, so the apply is exactly the previewed change.
  - **Mail:** the supervisor already could mail each pool. `mail dev.N` needs `mail:<group>.dev.<n>`, which `provision` now grants the supervisor, one per developer.
- **Limits:** commands that rewrite files (`set`, `provision`, `pause`, `resume`) need `cardea-kernel` to write the host file's and the provisioning file's directory; the package leaves `/etc/cardea` (`root:cardea-kernel`, `0750`) as it is, so that is the host owner's decision (runbook). Read-only commands and `mail` need only read access.
- **Verification:** `apps/api/tests/service/test_team_cli.py`: every command, the fixed-host and trusted-file checks, the sudo argv, the one-JSON-answer helper, the sudoers rule's exact text, the staged kit and the packaged `provision` command. Not run: a package build, an install, or a real SVID.
- **Revisit trigger:** a first run on a real host (record it here), or a second account that needs the supervisor identity.
