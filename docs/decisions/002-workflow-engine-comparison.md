# ADR-002 — Workflow Engine Comparison

Date: 2026-09-22. Owner: kernel/runtime. Milestones: R05/M1, with R08–R11 integration implications.

**Status: proposed; first comparison complete, adoption undecided.** Seventeen projects were screened using primary documentation, repository metadata, release records, and license files. The initial screening did not execute any engine. Subsequently, [ADR-003](003-dbos-fit.md) records an isolated DBOS experiment on SQLite and PostgreSQL, including integration gaps. [ADR-004](004-temporal-fit.md) adds Temporal development-server observations. [ADR-005](005-absurd-fit.md) adds Absurd PostgreSQL observations. [ADR-006](006-hatchet-fit.md) adds Hatchet native-sidecar observations. [ADR-007](007-runtime-integration-direction.md) selects DBOS for a bounded integration experiment; no engine is integrated into Cardea. The remaining 13 candidates have not had runtime tests.

## Initial Recommendation

Evaluate **DBOS, Temporal, Hatchet, and Absurd** with the same failure scenarios. DBOS offers an application-embedded Python approach; Temporal supplies a separate durable execution service; Hatchet combines task orchestration with durable waits; Absurd is a smaller PostgreSQL-native contender. Preserve Dapr as a broader-runtime alternative and Duron, Obelisk, and Continuum as emerging alternatives. Do not write a custom dispatch loop while this comparison is unresolved.

The accepted experiment order is **DBOS, then Temporal, followed by Absurd and Hatchet**. The first DBOS 3.0.0 experiment is recorded in ADR-003, using a disposable PostgreSQL instance and a separate SQLite profile. [ADR-004](004-temporal-fit.md) now tests the contrasting Temporal service model. [ADR-005](005-absurd-fit.md) covers Absurd and [ADR-006](006-hatchet-fit.md) covers Hatchet. The first pass of all four is complete, with differing partial acceptance coverage.

## Scope and Method

Searches covered durable execution, Python workflow libraries, PostgreSQL-native queues/workflows, standalone local engines, WASM runtimes, and projects emerging in 2025–2026. Examples: `open source durable execution workflow engine 2026`, `durable execution Python workflow engine Absurd`, and primary-source queries for Restate, Hatchet, Duron, Obelisk, and Continuum. Discovery results were followed to upstream documentation and source. This is a bounded survey, not a claim to have found every project or the absolute newest release worldwide.

“Modern” means durable external waits, recoverable execution, usable Python integration, explicit failure semantics, versioning, and an operable self-hosted deployment. Repository creation date, recent pushes, or stars do not establish correctness. Creation dates identify repositories, not necessarily original project launches. No popularity score is used.

The [source snapshot](r05-source-snapshot-2026-09-22.json) records observed release dates, default-branch activity, archived status, tagged license URLs and hashes, and Python package versions. All 17 repositories were unarchived at capture. Main-branch documents describe capabilities to investigate; they are **not proof those capabilities exist in every listed release**. Before execution, pin the engine, SDK, image digest, storage version, and feature availability together.

GitHub's designated latest release can differ from the newest publication because of backports, SDK tags, or release promotion. Temporal's designated version was 1.32.0 despite newer publications on older branches; Hatchet designated 0.107.0 while server 0.107.2 and Python SDK 1.41.0 were already published. The table explicitly screens the latter server patch. Development releases and release candidates are not substituted for stable candidates.

## Requirements That Decide Fit

- **Recovery:** acknowledged progress survives process restart; uncertain external effects are reconciled before any repeat. An engine's completed-step cache alone does not close the gap between an external effect and its recorded result.
- **Waits:** timers, external events arriving before/during/after registration, and task dependencies survive restart without lost wakeups. Event retention and deduplication must be explicit.
- **Ownership:** concurrent workers and expired/reassigned work cannot commit stale Cardea state or perform unauthorized new effects. Heartbeats, leases, and fencing are related but not interchangeable guarantees.
- **Authority:** grants never exceed live supervisor/ancestor authority. Recheck at admission, dispatch, retry, and resume; a persisted approval or replayed successful permission check cannot restore revoked authority.
- **Cancellation/deadlines:** distinguish a workflow marked cancelled from an actually stopped process tree. Preserve absolute task deadlines across queueing, retries, and sleep.
- **State and evidence:** versioned inputs/artifacts, stable operation identity and argument conflict checks, and verifier evidence precede task success. Preserve v0.1 receipts or migrate explicitly.
- **Operations:** one Debian host initially; Python 3.12; inspectable state, upgrades, backup/restore, bounded storage, and measured resource cost. New infrastructure is permitted only with documented benefit, not assumed cheap or expensive.

## What the Strongest Candidates Actually Document

These are source findings, not our test results.

**DBOS:** supports SQLite, while recommending PostgreSQL for production; SQLite uses polling. Durable sleep and workflow messaging can cover several wait types. Workflow timeouts begin at execution rather than initial enqueueing, so Cardea's absolute deadline still needs a broker check. Synchronous Python steps cannot be preempted by its async-step timeout mechanism. Its 3.0 migration guide also deserves a pinned-version review. [Database](https://docs.dbos.dev/python/tutorials/database-connection), [workflows](https://docs.dbos.dev/python/tutorials/workflow-tutorial), [steps](https://docs.dbos.dev/python/tutorials/step-tutorial), [messaging](https://docs.dbos.dev/python/tutorials/workflow-communication), [upgrade guide](https://docs.dbos.dev/python/upgrading).

**Temporal:** supplies workflow histories/replay, signals, timers, activities and worker coordination. A workflow history is per execution, not Cardea's database-wide event cursor. Activities must tolerate retries or use explicit retry/reconciliation policies; durable orchestration cannot atomically commit an arbitrary remote effect with its history. Pin the Python SDK and server separately. [Execution](https://docs.temporal.io/workflow-execution), [activities](https://docs.temporal.io/activity-execution), [Python messaging](https://docs.temporal.io/develop/python/workflows/message-passing).

**Hatchet:** documents durable tasks, sleeps, waits and child execution. Its recently documented embedded mode starts a separate engine process and a bundled PostgreSQL instance; it is not a pure in-process library. PostgreSQL messaging can replace RabbitMQ in that configuration. Documentation exposes version and checksum configuration, which should be pinned for experiments rather than accepting first-use downloads. ADR-006 subsequently tests public durable/child APIs with SDK 1.41.0 and the available native sidecar engine 0.107.0; this does not verify engine 0.107.2. [Durable execution](https://docs.hatchet.run/v1/durable-execution), [embedded mode](https://docs.hatchet.run/v1/embedded), [Python client](https://docs.hatchet.run/reference/python/client).

**Absurd:** workers claim tasks with expiring leases; its documentation explicitly permits brief overlap when a lease expires. Events retain the first payload for a name, so repeated events need distinct identities rather than reusing a name as a journal cursor. Cancellation is observed at checkpoints/heartbeats. These are concrete adapter questions, not reasons to dismiss the project. PostgreSQL 14+ and Python SDKs are documented; no extra orchestration service is required. [Concepts](https://earendil-works.github.io/absurd/concepts/), [quickstart](https://earendil-works.github.io/absurd/quickstart/).

## Newer and Less Familiar Projects

Absurd and Duron repositories began in late 2025; Continuum in May 2026. Their release histories and default-branch activity are captured separately. Obelisk offers a different modern architecture: WIT-typed WASM components and deterministic replay, with SQLite/PostgreSQL persistence. Duron emphasizes async Python, streaming and interruption. Continuum describes PostgreSQL fencing-token checks and an OTP-native recovery model. These expand the design space without establishing production suitability. [Absurd](https://github.com/earendil-works/absurd), [Duron](https://github.com/brian14708/duron), [Obelisk](https://github.com/obeli-sk/obelisk), [Continuum](https://github.com/Yyeger/Continuum).

For the next round, give emerging candidates the same tests and evidence rules as established ones. Do not treat a recent release as proof of safety or a small community as automatic rejection. A documented Python/storage/ownership gap may move a candidate out of the shortlist; an assumption may not.

## License and Maintenance Findings

Read the actual source license at the screened tag. Restate's BSL notice states that it is not an open-source license; its future conversion does not make today's release Apache-licensed. Inngest distinguishes its SSPL server from Apache SDKs and delayed Apache publication. Windmill distinguishes source-built AGPL code from mixed-license Community distributions. Dagu's current inspected release is GPL-3.0. Copyleft is not itself a failure of the open-source preference; packaging and distribution obligations must be respected. These findings classify artifacts, not authorize a particular commercial deployment. ## Integration Questions Before Selecting an Engine

1. **Choose a single owner of execution state.** If an engine owns scheduling/history, Cardea should map that state instead of running a competing lifecycle engine. Identify which existing implementation can be replaced, not only wrapped.
2. **Handle the two-store boundary.** An engine's PostgreSQL/server commit and Cardea's SQLite commit are not one transaction. Evaluate shared supported transactions or a standard durable outbox/idempotent reconciliation pattern, and test crashes between commits. Do not claim atomicity because both writes eventually succeed.
3. **Keep current authority at the effect boundary.** Replay may return a cached permission-check result. Authorization must run in the trusted broker for every new effect attempt, with fresh supervisor/ancestor state. Workflow arguments, headers and events are not authority.
4. **Keep workers away from privileged storage and credentials.** A library expecting direct database access belongs in the trusted runtime service; untrusted tools still run through the host adapter. Engine adoption does not make workers sandboxed.
5. **Map identities, events and results explicitly.** Preserve task/operation idempotency and receipt digests. Engine event offsets may be per workflow or signal key, unlike Cardea's global cursor. Artifact references and verifier output remain application data unless equivalent facilities are demonstrated.
6. **Distinguish retries from new tasks.** Engine attempts may replay inside a task. A terminal Cardea task cannot silently reopen; operator reruns must produce an explicitly linked new task or a versioned contract change.

## Common Fit Test Specification

At the initial screening, every case was **NOT RUN for all candidates**; the accompanying source snapshot preserves that point in time. Current DBOS results and remaining gaps are mapped to F01–F12 in [ADR-003](003-dbos-fit.md#r05-acceptance-status). [Temporal results](004-temporal-fit.md#r05-acceptance-status) add a development-server profile, and [Absurd results](005-absurd-fit.md#r05-acceptance-status) add a PostgreSQL/synchronous-SDK profile. [Hatchet results](006-hatchet-fit.md#r05-acceptance-status) add a native-sidecar profile; candidates outside the shortlist remain unrun. Record engine/SDK/storage versions, configuration, fault point, observed state/effect count, trace and pass/fail/blocked result. Test a minimal adapter with fictional data; do not connect real agents or services.

| ID | Experiment | Required observation |
|---|---|---|
| F01 | Save one output, hard-kill worker, restart in a new process | Acknowledged output survives; the completed safe step is not repeated. |
| F02 | Send event before registration, during registration, while down, and twice | No lost wakeup; documented deduplication and payload ordering; unrelated events do not wake the task. |
| F03 | Restart during timer and child-task waits | Timers remain durable; child success/failure/cancellation follows an explicit mapping. |
| F04 | Pause worker A past expiry; let worker B claim; then resume A | Old ownership cannot commit Cardea state or new broker effects; any engine overlap is visible and fenced. |
| F05 | Commit a fake external effect, kill before recording its result | No blind second effect; surface uncertainty and reconcile using recorded intent/evidence. Disabling exception retries alone is insufficient if crash recovery replays the step. |
| F06 | Submit the same operation ID with identical then changed arguments | Same request returns its receipt; changed request conflicts; retry cannot switch digest versions. |
| F07 | Revoke/disable supervisor while waiting, before retry/resume, and immediately before effect dispatch | Fresh authority denies descendants; cached checks, broader approvers and service credentials cannot bypass the ceiling. |
| F08 | Cancel with a child and a running process; expire an absolute deadline while queued | No new dispatch; host process descendants stop or are explicitly reported unreconciled. A cancelled status alone does not pass. |
| F09 | Crash between Cardea state commit and engine history/dispatch commit, in both orders | Recovery neither loses acknowledged work nor publishes contradictory terminal states. |
| F10 | Modify workflow code/schema while tasks are sleeping; upgrade and restore backup | Version strategy is explicit; receipts remain valid; unsupported resumes fail clearly. |
| F11 | Return an incorrect artifact with a success-shaped worker result | Trusted verification rejects completion and records inspectable evidence. |
| F12 | Cold start and idle/run measurement on Debian 13 | Record processes, services, RSS, CPU, startup time, DB growth, cleanup and install/restore steps. No performance ranking before measurement. |

F07 and F08 require the Cardea authority/host boundary, which is not implemented yet. Early experiments may use a clearly labeled test broker and fake authority source; passing those probes would not establish deployed enforcement or Debian confinement.

## Completion and Next Decision

This pass delivers the 17-candidate comparison, release/license evidence, a four-candidate shortlist, and common acceptance cases. ADR-003 through ADR-006 add isolated DBOS, Temporal, Absurd and Hatchet runtime observations. R05 remains open. No dependency, provider, engine, or service was added to the application. [ADR-007](007-runtime-integration-direction.md) recommends DBOS for the next bounded commit-boundary/ownership experiment. Production adoption remains undecided. Revisit the shortlist if a candidate fails a hard requirement, introduces substantial bespoke glue, changes license, or another maintained project offers a demonstrably better fit.
