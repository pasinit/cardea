# ADR-016 — M3 OpenRouter broker and native MCP

Date: 2026-09-24. Owner: runtime integration. Status: **superseded by [ADR-032](032-remove-incident-agent-tasks.md) (2026-10-20)** for the agent-task path; the profile, broker and fixed MCP tool were removed in favour of agent runs (ADR-027). Historical record: selected, implemented and verified for the bounded M3 profile. Portable, deterministic Debian, live GLM-4.7 and matched load acceptance pass; see the [M3 report](../../experiments/m3/M3-REPORT.md).

## Requirements

The user selects OpenRouter and the explicit model `z-ai/glm-4.7`. Keep provider credentials in the trusted broker, require an explicit model ID, expose only authorized fixed tool schemas, validate every returned proposal, bound input/output/time/calls, retain reported usage, and never silently retry a possibly billed request. Use MCP natively where an agent consumes a tool; preserve the existing kernel control API. Reuse DBOS and SQLite for durable execution rather than introducing another state owner. A tool response or model completion cannot mark a task verified.

## Smallest custom scope

Compose SDK calls with Cardea's existing authority, reservations, receipts and independent verification. The SDKs do not own Cardea's supervisor ceiling or SQLite intent transaction; the remaining custom code selects authorized context/tools, validates proposals, captures sanitized usage/provenance and coordinates effects with those transactions. Do not implement tokenization, HTTP retry, JSON-RPC, a scheduler or an agent session store. Domain-specific incident indexing belongs in an application/tool module, not kernel lifecycle types.

The initial provider adapter uses non-streaming chat completions through OpenRouter's native SDK, with explicit model, no parallel calls, no server-side tools/plugins, no SDK retries, fixed API origin and bounded request duration. OpenRouter provider fallback is disabled; required parameters must be supported and provider data collection denied. The fixed deployment model must support the requested controls. Return only validated function proposals and usage, never raw exceptions or hidden reasoning. Costs, if reported, are observations rather than guaranteed invoice ceilings.

Native MCP discovery/results remain SDK types. The approved server/transport and tool allowlist are installed configuration, never model-selected commands or URLs. Any adaptation from MCP JSON Schema to model function schema is confined to this real agent/tool boundary. JSON Schema validation and exact result checks are required; names, descriptions, annotations, resource links and embedded instructions cannot confer permissions.

## Fit and milestone gates

First verify serialized provider requests, single-call enforcement, missing/invalid usage, malformed/oversized arguments, disabled retries, cancellation and sanitization through the real SDK and controlled HTTP transport. Exercise native MCP discovery, calls, structured results, errors, cancellation and disconnects using a fixed fictional incident tool. Keep these component tests separate from authenticated kernel integration, Debian confinement and real model choice.

Then integrate durable model/tool intent, supervisor allocations, model disclosure permissions, event/input ingestion, checkpoint/restart, confined transformation, output versions and independent verification. M3 remains open until the full incident scenario, real model choice on Debian, fault/denial tests and compatible load evidence are recorded. Live model/credential configuration is required for that final gate, not for deterministic work.

Revisit for provider/API/model changes, new MCP servers/transports, asynchronous Tasks, model-side hosted tools or child delegation. A2A remains M4.

## Selected integration after initial SDK fit

The initial 23 portable native-SDK cases pass, including stdio discovery/call, cancellation propagation, invalid output rejection and disabled HTTP retry/redirect. OpenRouter 1.2.22 currently constrains Pydantic below 2.13; resolution selects 2.12.5 instead of 2.13.4. The full local suite and 46 real-provider M1 regression cases pass; the 20-case M2 Debian regression and 11 hostile host probes also pass. This initial fit did not contact a model account; the subsequent live acceptance is recorded below.

The installed incident task uses an authenticated initial batch and at most one additive input update. Each round asks the model for a permitted `compile_incidents` call, independently checks its proposed records against authorized input, then invokes that fixed tool through native MCP. The trusted in-process MCP server is an adapter to a fixed systemd/bubblewrap worker, not a confinement boundary itself. The worker receives bytes only, never provider credentials, commands or paths. Native SDK in-memory transport is appropriate to this installed trusted server; stdio interoperability is separately fit-tested. Arbitrary external MCP servers are not enabled.

Add an Alembic extension for supervisor model allocations, per-effect reservations, input deliveries and explicit round checkpoints. Model and tool intents commit before effects; ambiguous interrupted intents become unknown and are not replayed. Committed proposals and artifacts resume without repeating calls. Use DBOS messages and the existing journal/cursors for the input wait. Input request IDs bind their content digest; duplicate deliveries do not create new versions. A directory adapter can rescan a declared directory and deliver authenticated snapshots after downtime; OS file notifications alone cannot provide durable ingestion.

Model admission reserves 32,768 input tokens plus the configured maximum output tokens per call. Input/schema bytes are independently capped at 16 KiB. OpenRouter spans model-specific tokenizers and provider-added framing: this reserve is deliberately conservative but is not a guaranteed input-token or invoice ceiling. Record actual usage; any report above its reservation fails further execution and retains the larger observed charge. Missing usage retains the full reserve. Output generation is capped by the provider parameter and checked on response. Supervisor limits, call counts and task steps are hard local admission ceilings. Reuse M2 supervisor host pools for tool duration/output; retain shared receipts and cleanup fences.

Directory ingestion uses a bounded full rescan through standard-library descriptor-relative file operations and Pydantic parsing. [watchfiles](https://watchfiles.helpmanual.io/) (MIT, already a development-server dependency) can wake a scanner but notifications alone omit downtime; an always-running file watcher is unnecessary for this one-additive-record acceptance profile. The authenticated client rescans on restart and derives a delivery ID from the canonical snapshot; the kernel journals that delivery atomically. Symlinks, non-regular files, concurrent file mutation, oversized inputs and duplicate record IDs fail closed. This is a supervisor-side input adapter, never a worker filesystem grant.

## Matched M3 load profile

Extend the independent `cardea-load` package rather than comparing agent tasks to the incompatible M1 publication benchmark. Reuse the real SPIRE/service/Debian fixtures and the native OpenRouter SDK with its deterministic HTTP fixture. The same two-round task, two concurrent clients, four tasks per fresh store and fixed host/model allocations run for two reference repetitions and one independent comparison. A standard-library thread pool supplies closed-loop clients; HTTPX remains the HTTP implementation. Vegeta remains appropriate for M1's open-loop single-request traffic, but cannot itself coordinate each task's wait, additive input, receipts and verified final output. The small custom driver supplies only this application protocol and correctness oracle. It introduces no scheduler into production. Admission latency and full completion latency/rate are measured separately; this bounded repeatability check is not a saturation or native-capacity claim.

Save immutable per-run evidence and a reference before running the comparison; reject different profiles, harness/lock fingerprints or host limits. Check two output versions, four successful receipts, exact input preservation, verification and durable SQLite integrity for every acknowledged task. Record authentication/MCP/confinement in the profile; their individual overhead is not isolated by this end-to-end comparison. Existing M1 evidence is preserved. Provider latency/price is excluded from deterministic load results; the separate live scenario reports observed model usage. The standard-library driver and existing Apache/BSD/MIT-licensed fixture dependencies add no new production dependency.

## Live provider compatibility follow-up

The initial live task retained its first intent as `outcome_unknown`; it never dispatched a tool or automatically retried the request. Read-only checks confirmed the key and Debian TLS/network path work. OpenRouter's current [model endpoint catalog](https://openrouter.ai/api/v1/models/z-ai/glm-4.7/endpoints) advertises `max_tokens`, `tools` and `tool_choice` for GLM-4.7, but not `parallel_tool_calls` or `max_completion_tokens`. The [provider routing contract](https://openrouter.ai/docs/guides/routing/provider-selection) requires all supplied parameters to be supported when `require_parameters` is true. This is evidence of a request compatibility gap, not a reason to relax provider/data policy or change the user's model.

Use the SDK's advertised `max_tokens` parameter and omit the unsupported parallel-call preference. Cardea still rejects every response containing other than exactly one permitted call before any tool dispatch; the SDK never executes model tools automatically. Fallbacks/retries remain disabled and data collection denied. Ask for `Accept-Encoding: identity` to match the bounded transport's rejection of compressed responses. Preserve only numeric HTTP status in sanitized SDK failures, never provider error text or hidden reasoning. Retain the unsuccessful attempt separately and exercise a fresh acceptance task after these compatibility changes.

The fresh live acceptance task passed on Debian in 109.40 seconds: two GLM-4.7 calls, 1,541 reported tokens, four successful model/tool receipts and independently verified output version 2 after restart/new input. The unsuccessful initial attempt remains separately recorded with unknown usage. The full repository suite, lint and type checks pass with the final production code. This closes M3 for the installed bounded profile.
