# ADR-030: Small-Host Profile

- **Date / owner / milestones:** 2026-10-15; packaging and identity maintainers; ADR-022 gap #10 (C6).
- **Status:** selected. The deployment kit is in `deploy/small-host/`, and its examples are validated by tests. Not yet installed or measured on a real host.
- **Requirement:** run Cardea for one client application (Telos) on one small VM (2–4 GB) with authenticated machine callers over a private network. The supervisor ceiling and every identity guarantee must hold, without operating an OIDC provider.

## Decision

| Concern | Choice | Alternatives and why not |
|---|---|---|
| Identity provider | SPIRE server and agent only (v1.15.3), SQLite datastore. Cardea already validates JWT-SVIDs (ADR-009/010). | Keycloak or another OIDC provider: needed only for human logins and too heavy for 2 GB. OIDC stays optional in `ServiceConfig`. |
| Node attestation | `join_token`, one token per node, generated by the host owner | Cloud-provider attestors (`aws_iid`, `gcp_iit`) do not exist for this provider. `x509pop` needs a separate PKI. Join tokens are single-use and auditable in SPIRE. |
| Workload attestation | Kernel: `unix:user:cardea-kernel`. Telos: the Docker attestor plus a spiffe-helper sidecar (v0.12.1) that writes a JWT-SVID (audience `cardea-kernel`, 5-minute TTL) to a shared volume | Embedding the SPIFFE Workload API client in Telos would add a dependency to every Telos deployment. On a single-tenant Docker host, whoever can start a container with the sidecar's label can obtain the identity; root on that host already implies this. |
| Transport | ADR-025 TLS 1.3 listener with a certificate from a private CA (`make-tls.sh`); Telos pins the CA | SVID-based server certificates rotate hourly, and the listener reads certificates only at startup (ADR-025 open item). Revisit when hot reload exists. |
| Process supervision | A systemd unit with a `MemoryMax` for the whole service cgroup | Docker: the confinement profiles need systemd and cgroup delegation on the host (ADR-012, ADR-028). |
| Telos authority | One `telos` service principal is the supervisor. Each Telos user gets an exact namespace (`telos-<user>`), each agent a principal (`telos-<agent>`). Grants: the kernel rights, `models.invoke`, `tasks.schedule` and the installed operations. | One Cardea principal per Telos user would need Telos to hold or broker per-user credentials it does not have. Namespaces keep users' data and schedules apart under the ceiling. |

## Consequences and limits

- **Telos is trusted across its namespaces.** A compromised Telos host can act for every Telos user within the provisioned grants. This is the same trust Telos has today, but bounded by the namespaces, the grants and the expiry dates.
- **Certificate rotation needs a restart.** The private CA's key must be kept offline.
- **Memory is unmeasured.** Cardea, SPIRE and a Claude session together on 2 GB is the target; measure with real routine runs before relying on it, and use a 4 GB VM otherwise.
- **Sessions are not confined yet.** Confined workers for agent sessions and browsers (ADR-028) need that profile enabled here once accepted on Debian.
